## 1. What to do

| Block | Rule |
|----|------|
| Positioning | Hunt the same way even when it is not in the table. When the site contradicts the table, the site wins. On entering a site, if you recognize a familiar shape you may look at the short table for the opening few shots; if it does not match or is already fixed, drop the table and hunt per the site. Recognizing a framework/parameter only accelerates the current site — recognizing it does not license an all-of-FOFA sweep of the same wrapper or breaking the one-seed loop. `*src-notes.md` / exhausted clusters = give-up signals, false points — not a reason this root domain never looks at new paths again. |
| Where it goes | Steps/encoding/disproof/long chains → the matching existing module under `C:\Users\chu01\.claude\skills\src-6k\knowledge-base/`. A one-line technique or pointer → `knowledge-base/breakthrough-short-table.md`. This engagement's formal report (medium is written here too, it just does not enter the short table) → `Desktop\{task}_SRC-hunting\reports\`. This engagement's URLs / extracted JS → task root `assets/`, `js/`. The task root must not contain retrospective.md / notes.md. Writing the short table or editing one pointer line must take under half a minute; if it will not take shape → do not write it, keep hunting. |
| Bar | What enters is the technique, not this bug, not some host. **Passing the bar** = open `vuln-report-format.md` on disk, the "vulnerability severity" cell, and compare **what the body text actually achieved** against those clauses; the title or the words "high severity" already written do not decide it. Read the current format draft on disk. This file does not copy, modify or re-grade those clauses. If not one clause is met → treat this piece as having no high severity and do not enter the table. High severity ≠ a pass. Self-hunted: the source must be a high or critical already written to the task's `reports/`. Dropped into the conversation by the user: the conversation must contain a report/payload body that can be compared (it need not be in a task folder first), still compared against format; merely saying "there is a bug" with no comparable body → does not enter. Medium is only written to the report — not into the short table, not proposed for entry. Medium does not enter even if the user says to release it. Not being in the library ≠ it should enter. Not a bug in the first place, isomorphic re-confirmation, a path that only exists on this host → does not enter. |
| Three questions | Only asked after passing the bar; if you cannot answer or the answer is negative → does not enter the table, and do not ask the user. ① Switching to another site or another product of the same shape, can you still recognize A and hit it as B? ② Is what you recognize only this host / this one path / a field name inside one product? If the same shape elsewhere cannot recognize the same set → does not enter (single-site memo; still write the report). This is not a field-name blacklist: if next time the same shape can still be recognized the same way and yields a new recognition method, it still enters per the three questions. ②.1 A generic shot with no new recognition does not enter: what you recognized is only swapping ids, empty passwords, omitting, auto-incrementing list ids, dropping `'` on every path → does not enter (that is `dig-scope`'s job, not something blocked by whether the table has a row). Only with a new recognition (control gate, encoding position, false point, a mis-hit that would look like no bug) do you go further. Write what you recognize as a shape; writing "just swapping ids again" or a field name is forbidden. If deleting this row still leaves next time's similar site hitting it the same way → does not enter; if it would not, because you first have to recognize an easily-missed shape → then it enters/is supplemented. ③ Open the existing short-table row: is what you have extra a new recognition, a new technique, or a new false point? If you cannot tell the difference, do not write; if you can and a similar row already exists → only supplement the original row, details go into the module. Only when all three questions pass, there is no similar entry in the library, it can be written as "recognize A → hit B", and it can still produce high severity next time → add a new row. For a shape that disproves "this will be treated as a bug again later" → only edit the false-point column. For too-narrow see the next cell; do not fold it into this one. |
| Too narrow | See three-questions ①②; no separate tier. If switching to the same shape cannot recognize it (this vendor's own endpoint name, latency, activity number, dead path) → does not enter, not supplemented. Even if it was broken through, it is only a single-site memo. A same shape that ① already released does not count as too narrow. Using "change N sites" or "one product line" to block something ① released is forbidden. A new false point/new technique for an existing row is still supplemented per three-questions ③; too-narrow does not block ③. |
| Two tracks | Self-hunted and written down in this window: pass the bar first, then the three questions. If it passes and the library has no such entry → enter the short table, do not wait for "release", do not ask. If a similar entry exists with a new differential → only supplement. Bar not passed or three questions not passed → do not write the table, and do not ask. The user themselves drops a report / payload / technique into the conversation: understand it yourself first. With no comparable body → does not enter. With a body, pass the bar first (compare against the body in the conversation per format), then the three questions. To enter the short table or supplement a module you must pass the bar first. Medium never supplements the short table or a module. "The module has a new differential" only applies to high/critical that already passed the bar: when it is not new enough to open a row, only supplement the original module — this is not an opening for medium. If it passes → supplement directly, do not wait for "release", reply one line: understood/supplemented or understood/not supplemented. Only-harms-yourself, half a chain, isomorphic with no differential, duplicate of a generic internet polyglot, too narrow, bar not passed, a generic shot with no new recognition → not supplemented. Stuffing one high-severity article per row into the short table is forbidden. Applying "wait for release" to bugs you hunted yourself is forbidden. |
| Existing similar entry | If the idea is already in the short table/module → do not open another row, do not start another article. Isomorphic re-breakthrough with no new technique differential → do not touch the file (still write the report if it is due). If the recognition/technique/false point/encoding/disproof has something new that is usable next time (it can still be hit on another site, not this vendor only) → only supplement to strengthen that existing row or article: edit the same short-table row, merge details into the original module. Only when it is so new that it is no longer the same "recognize A hit B" → add a new row / new pointer. What is supplemented is the technique differential, not this host, not this report's summary. What you recognize stays a shape (framework/parameter/business surface); this vendor's product name, full path, and vendor-specific field enumerations go into "where to hit" or the module — appending them to "what to recognize" as a named checklist is forbidden. The success criterion may only be clarified or tightened; adding weaker "signature passed / parameter missing / auth passed" as a breakthrough is forbidden. Real key values and full JS are not supplemented into the library. This is incremental supplementation, not reorganizing the old library. |
| Who writes | Single window (no sub-threads): pass the bar, then the three questions, then write/supplement yourself. Site-hunting sub-thread: do not modify `breakthrough-short-table.md` or knowledge-base modules; after a high severity is written to disk, write one line in this site's `DONE.md`: `proposed: recognize…hit…` / `supplement: which row gained what` / `not entering: bar not passed or three questions not passed or no new differential`. Controller: when the sub-thread returns, pass the bar first, then re-check the three questions, then write/supplement the short table; DONE is not a knowledge base. When spawning a sub-thread the delivery checklist must include iteration. Writing only "JS + inventory + matrix + write report" is forbidden. The sub-thread must read this file from disk at the start; trusting only a stale copy frozen in the conversation is forbidden. |
| Does not block site switching | Seed search / site switching / seed change / idle jump / one-seed loop obey only `dig-scope-workflow`. This file governs the short table and does not raise the site-switch bar. **Medium: first dig the same object bigger, then switch** (`dig-scope` §4.3); merging the short table still does not block site switching. With a high-severity report → spend half a minute before switching to write proposed/supplement/not-entering; if the bar or three questions fail, writing "not entering" completes the iteration. The controller may merge the short table later; it does not block going through `dig-scope` §4.3. High-value leads broken through mid-way do not write the table; once the report is on disk, pass the bar then the three questions. Entering/supplementing the short table is not clocking off. 15–20 minutes of idling: if there is no high severity, do not burn time on the short table. No report = no proposal. The user says clean up: the controller first runs the unmerged proposals through the bar + three questions, merges only what passes, discards the rest, then deletes dig. Waiting for the controller to finish merging the short table before switching sites is forbidden; so is grinding proposals when nothing was found; reading "missing iteration" as "cannot walk §4.3 until the short table is merged"; and reading "does not block site switching" as "switch as soon as a medium is written". |
| How to read | Saving tokens is a side effect, not a cage. Modules that should be opened and details that should be read must be opened. Entering a site: ① read `breakthrough-short-table.md` first; ② if you recognize it and it matches → use it for the opening few shots, and pointer rows must open the corresponding module for details — copying a half sentence from the short table is forbidden; ③ after those shots, immediately return to this site's inventory (`dig-scope` §4: describe this surface first, extract keys from JS, queue the responses). When a fat JS/inventory/response surface shows a shape that **executes, renders templates, or calls a command-bearing RPC/tool** → open **that corresponding article** as the opener (not reading the whole RCE library, not going off to jailbreak); after hitting, return to the inventory; if nothing was extracted do not invent parameters, RCE is N/A only when `dig-scope` §4.2.1 says there is no entry point, other types are hunted as usual. Treating word-table examples as an allow-list is forbidden. Without an account, hit the four-piece set on surfaces with a differential; with an account, do object graph / id swapping first (§4.2.3), and hit the four-piece set on those business parameters; ④ only open `*src-notes.md` in parallel with the short table if it exists on disk; its absence is not a deficiency. A dedicated article is wording/dead-end clusters, not a short-table row, and not this site's inventory. If the file is not long → open it whole. For very long ones you may open the named section first; if it is not enough, needs comparison, needs encoding/disproof → continue opening the needed sections of the same article. If the site does not match and you need a different technique → any relevant section of the same article may be opened. The only prohibition is reading dozens of knowledge-base files end to end at every site. If the table is empty, does not match, or has never covered this class → hunt directly; do not stop and wait for the table. Techniques you natively know need no library first; open it whenever details are needed on site. Opening a module ≠ only testing that one shot from the table; the four-piece set, IDOR/logic, this site's inventory and surfaces absent from the table are hunted as usual. |
| What a row looks like | What to recognize: framework or parameter/business shape; writing it as some vendor's some product's some path or a checklist is forbidden. Where to hit: path or parameter, a way to try rather than the only entry; mark "no login" or "needs session"; two sentences max, more goes into the module and the short table says "see xxx.md". What counts as success: the differential and what you obtained, and it must answer what of whose was gained over baseline; writing only "endpoint 200" is forbidden, and using a weaker success condition to lower the original bar is forbidden. False points: only write "this shape is simply not a bug". |
| False points | A false point records only that the shape is not a bug. Writing these into false points is forbidden: "this site did not inject", "this site 401", "this time it timed out". Not breaking through this time = this site's on-site reality; the same technique is still used on the next site. Applying the table to the current site and missing → only means this site does not work. Marking the whole row invalid, deleting the whole row, or treating the technique as nonexistent next time because of this is forbidden. Only when you confirm "the shape was never a bug / the whole premise of the technique is gone" do you edit the false point or delete the row. If unsure, do not edit the table; keep hunting. |
| Short table got fat | Follow this order; deleting first is forbidden. ① Merge: several rows with the same "what to recognize" become one row. After merging, "what to recognize" is still a shape, not "product A or product B or path C". ② Split out: when a cluster cannot be said in one row → merge the details into the matching existing module and turn the short-table row into a one-line pointer; if there is no matching module, create a new one named after the technique. Splitting `breakthrough-short-table-2026-08.md` by date/by task is forbidden. ③ Delete only these: junk false points confirmed not to be bugs; techniques whose whole premise is confirmed gone; rows mistakenly written in with no substance (including single-site memos mistakenly written into the table). ④ Do not delete: technique rows that can still produce high severity. Uncommon ≠ void. Missing on one site ≠ the technique is dead. Going through the old table cutting rows because "from now on only high severity is collected" is forbidden. Pinning a field name that failed the three questions once as a permanent blacklist is forbidden (not entering governs this write, not that the word may never be a recognition). Around 80 rows is only a reminder that steps 1–2 are due, not a quota and not "delete when you reach it". Unsure whether to keep → keep, and keep hunting. |
| Module got fat | When one article is so long that finding a technique takes ages → split it into two by technique/type and point the short-table pointer at the new one. Splitting the library by month, moving the old long text into the short table and then deleting the old library, or copying the short table and module text into each other (details in one place only) is forbidden. Volume may grow by having more matching articles in the folder; each read is still the short table + the one article you need. |
| When to touch files | A high severity you hunted yourself in a single window: pass the bar, then the three questions → write/supplement the short table in the same round; do not wait for "release". Bar or three questions not passed → do not write, do not ask. A high severity a sub-thread hunted itself: only write this site's DONE proposal/supplement/not-entering; editing the short table directly is forbidden; after the controller takes it back, pass the bar then the three questions, then write/supplement. A report / payload the user drops in: look at it yourself first; if there is a comparable body and it passes the bar + three questions (or it already passed the bar and you are only supplementing a module differential) then supplement, do not wait for "release"; if it is not worth it, reply one line "not supplemented". Medium is only written to the report — not into the table, not proposed, not supplemented into a module. When a shape is truly confirmed not to be a bug → false-point column. Switching site / switching seed / clocking off: do not write a separate retrospective. Starting a new task / spawning a sub-thread: start by writing `{name}_dig/THREAD_READ_ME.md`; the spawn delivery must include iteration. Read this file from disk. |
| How to use it at the start | The opening few shots hit only the current site. Pointer rows must open the corresponding module. ## 2. What not to do

| Item | Rule |
|----|------|
| Does not enter the short table | Logs of nothing found; FOFA hit counts; what was hunted on some site today; a pure login-wall process; same-wrapper re-confirmation; a path used only once; a target host with no submitted report; full tokens / real key values. Medium does not enter even when broken through. Mislabeling (open format's "vulnerability severity" and compare against the body — not one clause met) counts as no high severity and does not enter; a title saying high severity does not decide it. A generic shot with no new recognition (swapping ids, empty passwords, omitting, auto-incrementing list ids, dropping `'` on every path) does not enter. Entering the short table requires passing the bar first, then the three questions. Not entering the short table ≠ testing one less class in the matrix. Login / reset / rebinding / ticket exchange are still tested per `dig-scope` §4.2.2. |
| Forbidden | Passing a summary off as hunting progress; still polishing wording more than half a minute after starting the table. Writing the short table as a diary, weekly report, or some host's file. Entering with no substance; entering just because it is high severity; discarding because the library lacks it; opening another row when the library already has it; not supplementing the original row when there is a new differential; changing "what to recognize" into a product/path name when supplementing; writing the success criterion as signature passed/parameter missing/endpoint 200; forcing a supplement for something too narrow (same shape cannot recognize it); using it as teaching material to write junk isomorphic reports (testing is fine). Copying the short table mechanically; not hunting because the table lacks it; treating the table as this site's only checklist. Deleting a technique because one site missed it / writing "not broken through" as a false point. Deleting the old library to prevent bloat, deleting rows that can still produce high severity, splitting a pile of short tables by date, reading the whole library at every site. Using "save tokens / read only sections" as an excuse to open fewer modules or test one less class. Still waiting for the user to say "release" before entering a high-severity report you wrote yourself. Still idling waiting for "release" on something the user dropped in that you already understood and is worth supplementing. Using the table to break the one-seed loop. Using "iteration" as an excuse to hunt less, search less, cover fewer classes. Not writing the thread briefing when starting a new task; spawn delivery stopping at "write the report"; a sub-thread editing the short table directly; the controller not collecting proposals. Reading iteration as blocking site switching / as "walk §4.3 only after the short table is merged". Tidying the existing knowledge-base body text for the sake of the short table. Reading "no execution-class key extracted" as "this site never tests execution"; treating execution-class examples as an allow-list and not hunting execution surfaces outside the checklist; elevating RCE above id swapping/password change for the whole engagement as the main line; opening a new FOFA seed on recognizing an execution-class shape; reading "open a module" as "only test that one shot from the table" or switching to jailbreak work; giving the whole RCE section N/A because no keyword was seen on the home page (inventory/capture/response not yet examined). |
| Whether to write | Governed only by `vuln-report-format.md`. This table does not decide whether CORS / code sending / upload are reported; it only says medium does not enter the short table. The short table and modules do not grade severity and do not build a second suggested-severity table. Long details go into the matching old module; the short table keeps only a pointer. |
