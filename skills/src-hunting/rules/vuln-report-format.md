# Vulnerability report writing format (permanent · the only one)

> **2026-08-19:** The report rules are just these two parts.  
> **From now on, report rules change only these two tables in this file.** Adds, removals and changes all live here; writing them into Agents, src-value, dig-scope or other files is forbidden.

For per-class details of what to collect, you may still consult `src-value-hunting.md`; **whether to write, how to write, and where it goes** are governed by this file.

---

## 1. How to write the body (layout + 8 blocks)

Describe in first person, in plain language, what I managed to do; for impact, write only the damage that can ultimately be caused (the full permission surface; give examples where you have them, do not invent what you have not hit). It is not a step list. No popular-science. Written for a security reviewer.

| Block | Rule |
|----|------|
| Vulnerability title | One line. Whose site, what was accomplished. "Anonymous" = there was no login state when breaking through, not "omitting the credential also works". Only write "anonymous unauthenticated" when there is no login state; using "not logged in" in place of "unauthenticated" is forbidden. With a login state, writing "anonymous"/"anonymous unauthenticated" is forbidden; touching someone else's object is written as "IDOR". No login state + someone else's → both "anonymous unauthenticated" and "another person's" must be present, do not write "IDOR"; with a session + someone else's → write "IDOR", optionally with "another person's". When it can be done in bulk, include "arbitrary" or "bulk". Details in the anonymity gate. |
| Target site URL | `Target site URL: https://…` — the site a human opens. |
| Vulnerability severity | Write only medium, high or critical. It must first be an actual IDOR or unauthenticated access. **Critical** (at least one met): a command ran; you entered someone else's account or changed someone else's password/binding (logging in with a real human account and getting a real session goes here, not into high); money really moved, or a status like hiring/claim settlement/release really changed. **High** (not critical, at least one met): it identifies a real person (phone/ID card/bank card/ID photo); cloud keys/tokens/database connection strings/a session usable as someone else (must pass the key-recognition gate: the fake-value control was accepted by production, and the key-recognition shot produced an identity or a list; not yet used to enter an account or move money. For a DSN/Redis/component, connecting and querying an identity or a list is enough — it is not a human's backend login account); injection that returned another subject's data; another person's unpublished business body (internal knowledge base, unlisted/unpublished detail, ticket body — and it is the body, not a title or summary). A personal-space diary/post/album behind a permission wall returning only titles or summaries → medium. Grading covers only the clauses above; jumping a tier just because you have one more field than the last report is forbidden. **Medium**: there is permission expansion or business sensitivity, and neither clause above is met. If unsure, do not write it. |
| Vulnerability description | The label "Vulnerability description:" on its own line, then a newline before the body. First person, plain language: use "I" to say what was accomplished (no login state: what I did without logging in; with a session: what I did by swapping my own session onto someone else's object). With a login state, writing "I did not log in" is forbidden; with no login state, writing "I used my own session" is forbidden. Manual-speak ("this endpoint can be called without authentication") is forbidden, and so is "the attacker". Breaking through with no login state: the type "anonymous unauthenticated" appears only in the title; in the description use "I did not log in" to state the fact, do not use "not logged in" as a type, and do not paste "anonymous unauthenticated." again at the start of the paragraph. The chain may be mentioned in plain language, but do not copy the endpoint table into the description (full URLs belong in the involved-endpoint list). Do not paste packets, do not write reproduction, do not list damage (damage belongs to impact). When hard-coded credentials/keys come from JS: the description must contain the complete real value plus the complete JS address (full http(s) path, not just the filename); the citation in the endpoint list cannot replace this sentence. The body must be line-broken; do not squeeze it onto one line. |
| Vulnerability impact | The label "Vulnerability impact:" on its own line, then a newline before the body. Write only the damage that can ultimately be caused. Write it fully according to the real permissions and data surface of the identity/key/data obtained once this door is open (recognized menus, role descriptions, already-reachable write endpoints, what this key can actually call — do not write guesses); do not scale it down to how many shots the reproduction took. For credential bugs the usual two shots are only a reproduction example, not the impact ceiling; impact is still written out for the whole surface of this identity. Entering the backend only proves you can see; the impact must still say you can change and delete; with an admin key, anything that can pull bills/refund/transfer must be written, without requiring you to actually refund one. Do not write about doors you did not open (if you only read role names, do not write that you can change prices; if the password change succeeded but the ticket exchange failed, do not write "can enter the account" into impact — put the boundary in the description, stated with "I"). It is not a step list: no first layer/second layer, no "I sent POST / changed a parameter / full packet". Each kind of damage on its own line, in plain language naming what is harmed (people, accounts, money, internal body text, can change/can delete). Where you have examples you must give them: for a leak, give one or two real names/phone numbers/addresses/IDs or internal titles; for a proven change, give what it was changed to. Permission surfaces you did not really hit (can delete, can refund) are still written as impact, but do not invent "deleted whom" or "refunded which one". If it can be done in bulk, write "can bulk leak/change", not how to iterate. Vague phrasing like "not limited to" or "and other sensitive information" is forbidden, and writing only "leaks personal information" without examples is forbidden. |
| Involved endpoint list | List only the endpoints actually hit in the reproduction steps, numbered 1, 2, 3. Each entry gives the full address and its source; when taken from JS, attach the full JS link; when taken from a page, attach the document URL. A JS file used only to copy parameters is cited as the source on that endpoint entry — do not list the JS or the home page as a separate entry. Do not list control requests or endpoints you did not hit. |
| Reproduction steps | Write them item by item as 1, 2, 3, keeping only the packets needed to break through, so a reviewer can follow them to the end. One full packet per step. A packet that only copies parameters, makes a control comparison, or takes a look at what the page looks like does not become a step. When the breakthrough evidence is on the page itself (identity page 200, XSS reflection), it still must become a step. Which JS file the parameters came from, or which field in the previous step they were copied from, goes into the description of the step that uses them, with the full JS link or endpoint address. The control (before the change / original site) also goes into that step's description — do not open another step and send another packet. Purely numeric iteration needs no source explanation. Each step's description is one or two sentences: what was sent, and what it therefore proves. Do not repeatedly write "not logged in / no Cookie" inside the steps. Do not write the response inside the steps and do not paste the response. After a packet you may not append the response or "expected". When the next step needs a decryption/signature result, make it a separate step: that step says how it is run, what it decrypts to, and what the next step does with it. Credentials/keys/private keys/an account already entered: if the key-recognition gate has not been passed, this report may not be written. The first step is key recognition or account entry (the fake-value control is written in that step's description; this shot must already have produced an identity or a list). Then normally one more read-only shot (if the first shot already produced one, switch to a different kind of read-only). If hitting again would touch production → submit with one shot only (that shot must still have produced an identity or a list). Using refunds/changing other people's data/transferring money to pad the example is forbidden. |
| Full packet (inside steps) | Paste exactly one copy-pasteable full packet per step. Host goes on the line immediately after the request line. Write Accept / Accept-Language: zh-CN / Accept-Encoding: gzip, deflate / User-Agent: Mozilla/4.0 (compatible; MSIE 7.0; Windows NT 10.0; WOW64; Trident/7.0; .NET4.0C; .NET4.0E; Tablet PC 2.0) / Connection: close in full. If there is a body, add Content-Type, Content-Length, Cache-Control: no-cache. Write Origin and Referer when the page has them. For a no-login breakthrough do not write Cookie; for a logged-in reproduction write the Cookie's complete real value. Forbidden: hunting with a session and then stripping the Cookie when submitting and labelling it anonymous. End the packet directly with [U+FF03]. Do not write "expected"; do not write or paste the response inside the steps. |
| Fix recommendation | Give a precise, actionable, well-targeted remediation matching this vulnerability, short and direct. |
| Layout | The vulnerability title, target site URL and vulnerability severity each occupy one line, with no blank line between them and no [U+FF03] separators. For "Vulnerability description:" and "Vulnerability impact:", a newline comes after the colon; the body must not continue on the colon's line. In impact, each kind of damage is on its own line, no first layer/second layer. Between large blocks use a single line containing a full-width [U+FF03]; half-width # is forbidden. In reproduction, each step is on its own line and a single [U+FF03] line separates items. After the reproduction, one [U+FF03] line, then the fix recommendation. No extra blank lines. |
| Output file | Put it in `Desktop\{task}_SRC-hunting\reports\`. The filename is exactly the vulnerability title line, with a `.md` suffix. Reports must not be scattered on the desktop root. CRLF. dig does not go into the body. With no bug, do not write an empty report. |

## 2. Whether it is written / where it goes

| Item | Rule |
|----|------|
| Do not write | Half a chain. Weak credentials that did not enter an account. Key-less shells (including a DSN without credentials, health, version, host-only with no password). Credentials/keys/private keys that failed the key-recognition gate (only a string copied, no fake-value control, the key-recognition shot produced no identity or list) → do not write. A read-only example after entering an account but with no identity or list → do not write. Placeholders/expired/real and fake giving the same error → do not write. Phone-number encryption/decryption keys (frontend AES/SM4/RSA, the salt/iv/key used to encrypt phone numbers, the kind whose PoC ciphertext can be decrypted) → do not write. Unauthenticated up/down only. Low severity, informational, configuration reminders, expired certificates (with no exploit chain), missing security headers. CORS. Unauthenticated SMS/email/verification-code sending. Slider/unlimited password guessing (without entering an account). Data readable by design, within your own account's permissions, public marketing data, fingerprints, temporary OSS image links, public documentation. CSRF that only harms yourself. An endpoint returning 200 with JSON. If unsure, do not write it either. Do not even mention "found a low-severity xxx" to the user. When code sending / a slider / a file channel is turned into account entry, password change, or an executable chain, write it as that bug, not as a standalone piece about "code sending" or "upload". |
| Write immediately | Medium, high or critical: once confirmed, write it into `reports/` immediately; hoarding until the end is forbidden. Not passing the anonymity gate or the key-recognition gate does not count as confirmed, and it may not be written to disk. |
| Anonymity gate | Before putting "anonymous" in the title, ask: did the breakthrough packet have a Cookie, and did this hunt have a login state? With a session → do not write anonymous, write IDOR instead, use "I used my own session" in the description, and write the Cookie's complete real value. Passing via omit does not count as "no login". |
| Key-recognition gate | **Copying a key is not a bug; write only once production has accepted it.** Private keys / PEM / SSH / AKSK / tokens / connection strings / JWT / a session usable as someone else — all pass the gate before being written to disk. Passing the gate = the fake-value control was accepted by production, and the key-recognition shot produced an identity or a list (SSH: a fake key gives Permission denied, the real key gives Hello <username>). Not passed → do not write. Submitting just because you copied a string = forbidden. If the first shot already produced an identity, switch to a different read-only that does not affect production; if hitting again would touch production → submit with one shot only (still must have produced an identity or a list). |
| Do not submit duplicates | If this task's `reports/` already has an identical bug (same type hit on the same url — swapping ids or adding parameters still counts as the same one) → do not write it. Same type on a different url, or a different type on the same url, are both written as usual. If the same bug grew bigger, edit the original article; do not open a new one. |
| Where keys go | Real key values and full JS go only into the formal report, never into the short table/knowledge base. |
| Cleanup | When the user says clean up: with no reports → delete the whole task folder; with reports → keep only `assets/` and `reports/`. Do not touch the account passwords stored in the browser. |
